# doubak-site-generator

[![test](https://github.com/Doubak/doubak-site-generator/actions/workflows/test.yml/badge.svg?branch=main)](https://github.com/Doubak/doubak-site-generator/actions/workflows/test.yml?query=branch%3Amain) [![Coverage Status](https://coveralls.io/repos/github/Doubak/doubak-site-generator/badge.svg?branch=main)](https://coveralls.io/github/Doubak/doubak-site-generator?branch=main)

> **这是源码仓库。** 项目主页在 **<https://doubak.com>**，生成效果样例参见 **<https://sample.doubak.com>**。

豆备（Doubak）的静态网页生成器。将 [canonical](https://github.com/Doubak/doubak-data-specs) 标准归档数据转换为 **Markdown + YAML front matter** 结构化内容树，供静态站点生成器直接渲染，提供完全离线、自主可控的个人豆瓣归档浏览体验。

```sh
npm run md    -- <canonical 目录> <bundle 目录> [产出目录]   # 输出 Markdown 与图片资源
npm run site  -- <canonical 目录> <bundle 目录> [产出目录]   # 进一步构建为完整 HTML 站点
npm run serve  -- <canonical 目录> <bundle 目录> [产出目录]  # 启动本地预览服务器
npm run deploy -- <canonical 目录> <bundle 目录> <仓库目录>  # 部署至 GitHub Pages 仓库
#                 [--include-private]                       # 导出私密数据（默认排除）
npm test                                                    # node --test，零依赖
```

**`md` 是本工具的核心产物，`site` 仅为默认的 HTML 渲染实现。** 若使用其他静态站点生成器，仅需运行 `md`，输出目录不含任何 Hugo 专有文件。

需要 Node ≥ 20。**无需执行 `npm install`** —— 运行时零外部依赖。

## 从归档到可浏览网页

```sh
# 1. 将抓取的 bundle 归档解析为 canonical 数据
cd doubak-data-parser
node bin/parse.js ~/downloads/exports ~/downloads/canonical

# 2. 结合 canonical 与 bundle 构建静态 HTML 站点
cd ../doubak-site-generator
npm run site -- ~/downloads/canonical ~/downloads/exports ~/downloads/site
```

构建完成后，直接**双击 `public/index.html`** 即可在本地浏览器中浏览，无需启动任何本地 Web 服务器（详见后文「无需服务器即可直接浏览」一节）。

为何第二步仍需输入 bundle：canonical 专注于结构化纯文本（方便使用 `jq` 检索，不包含二进制数据），而**图像等静态资源的原始字节存储于 bundle 归档中**，二者缺一不可。

**若仅需 Markdown 文本而不需构建 HTML，可运行 `npm run md`**（参数与上述一致）。产物中不包含任何 Hugo 专有配置或文件，可直接对接 Astro、Eleventy 或 Jekyll 等其他静态站点生成器 —— 详见「搭配其他静态站点生成器」。

npm 脚本对应的底层执行命令：

```sh
node bin/generate.js <canonical> <bundles> [out] [--no-theme]
node bin/site.js     <canonical> <bundles> [out] [--serve]
```

`--no-theme` 等同于 `npm run md` 的行为：**跳过内置的 Hugo 主题骨架**，仅输出 `content/` 与 `static/` 目录。默认情况下 `bin/generate.js` 会一并复制骨架文件，生成可直接执行构建的完整 Hugo 站点结构。若希望先定制 `layouts/` 布局模板或单独控制构建时机，可采用此流程。（`bin/site.js` 在指定 `--no-theme` 时会报错终止：缺少 `layouts/` 模板将导致 Hugo 无法执行渲染。）

产物目录结构：

```
20260806-site/
├── content/
│   ├── _index.md          首页：各媒介各状态的条目统计（均包含链接）
│   ├── movie/ book/ music/ game/ drama/   作品详情页，文件名为作品 ID
│   │   └── done/ doing/ wish/             各状态筛选汇总页，各自包含 _index.md
│   ├── note/ review/      日记与长评全文
│   ├── doulist/           豆列清单，包含条目及自定义评语
│   └── broadcast/         月度归档，2014-01.md … 2026-08.md
├── static/
│   ├── covers/            作品封面图片
│   └── uploads/           用户上传图片（广播配图、日记内嵌图）
├── hugo.toml              内置极简 Hugo 配置
├── layouts/               内置极简布局模板
└── public/                生成的完整静态 HTML 站点，双击 index.html 即可浏览
```

## Hugo 二进制管理：零 npm 依赖

首次运行 `npm run site` 时会自动下载 Hugo 官方二进制文件（约 20 MB，缓存在 `.hugo/` 目录供后续复用）。但它**不是 npm 依赖包** —— 项目的 `package.json` 中的 `dependencies` 为空。

npm 社区中的 `hugo-bin` 等封装包本质上也是下载官方二进制，但往往伴随复杂的依赖树。本项目的核心目标是极简、可审计与长期可维护性：**一个需要安装数百个深层依赖才能重新构建的归档工具，违背了长期独立归档的初衷。**

因此本项目采用极简的独立下载脚本（`src/hugo-bin.js`，约 40 行代码），遵循三项原则：

- **严格锁定版本**在 `HUGO_VERSION`，不动态拉取 `latest`。归档站点必须保证在多年后重新构建时产物完全一致，而动态 `latest` 会破坏可复现性。
- **SHA-256 哈希固化在仓库中**，而非下载后从同一远程源动态获取校验和。固定哈希值可供随时公开核对：
  ```sh
  curl -sSfL https://github.com/gohugoio/hugo/releases/download/v0.164.0/hugo_0.164.0_checksums.txt
  ```
  哈希不匹配时立即报错终止，而非发出警告后继续执行 —— 避免执行与仓库中固定校验值不一致的下载内容。
- **优先使用系统 PATH 中的 hugo**：若本地环境中已安装 Hugo，直接复用既有程序，不重复下载。

自动下载逻辑当前支持 Linux；macOS 与 Windows 用户建议通过系统包管理器安装（`brew install hugo` / `winget install Hugo.Hugo`），`npm run site` 会自动识别并复用。

## 无需服务器即可直接浏览

内置骨架同时启用了 `relativeURLs` 与 `uglyURLs`（两项配置不可或缺，技术原因详见「列表页与链接」一节）。构建产物中的所有站内超链接均为相对路径且精准指向物理存在的静态文件，因此**双击 `public/index.html` 即可直接在浏览器打开浏览**。实测全站 4794 个页面中的 94732 个站内链接，无效链接数为 **0**。

这一特性至关重要：归档数据可能在多年后直接从移动硬盘或冷备份中读取，无需依赖预先启动的 Web 服务器。

## 内置极简 Hugo 主题骨架

生成器默认将 `theme/hugo/` 模板复制到输出目录，生成开箱即用的静态站点。

选用 Hugo 的主要考量在于其为**单二进制程序**，无复杂运行时依赖；同时 `content/` + `static/` 的目录结构与 Hugo 原生结构完全一致，避免了多余的中间转换层。

主题骨架**不发起任何外部网络请求**：样式采用内建的 `static/site.css`，字体使用系统原生字体栈，无外部统计跟踪脚本与第三方评论组件。备份旨在摆脱对原平台的联网依赖，其自身也必须做到零外部 CDN 依赖。

### 视觉风格与版权声明

归档站点旨在提供熟悉一致的阅读体验，因此配色参考了豆瓣经典风格：绿色链接与强调色（`#007722` / `#41ac52`），以及橙黄色的星级评分（`#ffac2d`）。保持视觉一致性有助于降低阅读门槛，用户无需重新适应新的信息呈现方式。

**页脚强制包含「这是一份个人存档，与豆瓣网无关」版权声明，并在测试用例中严格约束。** 风格借鉴与官方身份声明具有明确界限，该声明即为二者的分界线。归档站点亦仅使用通用色块，不使用任何豆瓣官方商标。

所有颜色、间距与圆角参数均统一定义在 `site.css` 顶部的 Design Tokens 中，便于统一修改。

### 评分星级呈现逻辑

作品列表中采用图形化五星直观展示评分高低。

**未评分条目不渲染空星** —— 避免误读为「打分为 0 星」；实测数据显示 37% 的影视标记本身即未打分，属于正常状态而非数据缺失。单元测试对该逻辑有明确覆盖。

### 极简骨架便于自由替换

内置骨架仅包含 5 个模板文件，旨在保持最小依赖并便于替换。若需切换为现成的 Hugo 主题：只需移除 `layouts/` 目录并按对应主题配置，`content/` 与 `static/` 数据目录完全无需改动。

## 浏览器扩展中的同构支持

在无需安装 Node 环境的情况下，豆备浏览器扩展的「导出」页面可直接导出完全相同的 Markdown 结构树（包含完整的本地图片）。
底层复用了本项目完全相同的核心模块：`pages.js`、`projection.js`、`markdown.js`、`search.js`、
`yaml.js` 及 `image-index.js` 逐字节同步至扩展的 `src/vendor/site-generator/` 目录，
由双向 CI 脚本 `tools/sync-vendor.mjs --check` 保证代码同步状态。

为此，系统将**纯计算逻辑**与 I/O 操作进行了解耦分离，明确「输入输出差异由各宿主独立处理，数据解析与页面生成逻辑保持单一实现」：

| 拆分模块 | 原始位置 | 职责说明 |
|---|---|---|
| `pages.js` | `generate.js` | 将数据投影组织为页面层级树（首页、按月归档、状态筛选、小节、豆列及搜索索引），并维护 `MEDIUM_NAMES` / `SECTION_ORDER` / `STATUS_ORDER` |
| `image-index.js` | `images.js` | 负责图片索引映射、命名规则与完整性状态判定 |

`generate.js` 仅专注于特定运行环境下的 I/O 操作：从 WARC 中提取图片二进制流并将文本写入磁盘。
图片存储路径由调用方注入（通过 `images` 与 `coverBySubject` 映射表），因此 `pages.js` 完全解耦了底层存储是本地文件系统还是浏览器的 OPFS。

模块拆分不仅是为了架构整洁，更为了避免实现漂移：若不拆分共享模块，浏览器扩展将不得不重复实现一套页面排布与图片索引逻辑，极易引发判定规则的不一致（如根据错误的字段过滤、使用不存在的属性定位作品、或者图片去重逻辑存在差异），导致两端生成的站点出现隐蔽差异。

`test/portable.test.js` 严格确保这两个核心入口及其依赖链不引用任何 Node.js 原生模块，并验证页面生成逻辑未发生反向污染。

## 搭配其他静态站点生成器

```sh
npm run md -- <canonical> <bundles> <out>
```

产出目录仅包含通用的 `content/`（3131 个 `.md`）与 `static/`（3063 张图片），**不含任何 Hugo 专有配置文件**（测试用例严格约束该边界，避免误入 `hugo.toml` 等文件干扰其他静态站点生成器）。

这体现了「避免重复造模板引擎」的设计原则：直接产出通用规范的 Markdown + YAML front matter，兼容主流静态站点生成器生态，让用户能够直接利用丰富的现成主题。

### front matter 字段规范

除 `title`、`date` 与 `tags` 等通用标准字段外，所有扩展元数据均统一增加 `douban_` 前缀，防止与第三方主题预设的保留字段发生冲突。

| 字段名称 | 适用范围 | 说明 |
|---|---|---|
| `douban_kind` | 全量页面 | 取值包含 `mark` / `note` / `review` / `broadcast_month` / `index` |
| `douban_visibility` `douban_private` `douban_item_count` | 豆列 | `douban_private` 在可见性为 `unknown` 时同样置为 true，遵循严格保密优先原则 |
| `douban_medium` `douban_status` `douban_verb` `douban_rating` `douban_cover` `douban_meta` `douban_upstream_deleted` | 标记条目 | 包含媒介类别、标记状态、评分星级、封面路径与原站元信息 |
| `douban_published_at_raw` `douban_location` `douban_subject_url` | 日记与长评 | 记录发表时间、地点及关联作品详情链接 |
| `douban_month` `douban_count` `douban_with_text` `douban_images` | 广播月度页面 | 月度汇总指标、包含正文的条数与配图统计 |
| `douban_revisions` `douban_last_seen` `douban_url` | 全量页面 | 提供回溯关联 canonical 原始记录的必要溯源字段 |

### 迁移至其他 SSG 时的注意事项

以下注意事项基于产出文件的实际结构总结，供遇到迁移问题时参考：

- **`date: null`**（涉及 8 个历史文件）：豆瓣未记录标记时间的老数据。Jekyll 与 Eleventy 均能正常处理，但在 **Astro Content Collections** 中需在 schema 中明确声明为 `z.date().nullable()`。
- **文件名采用作品 ID 而非日期**（如 `movie/1309046.md`）：Jekyll 的 `_posts/` 默认要求 `YYYY-MM-DD-name.md` 命名，此类文件会被作为普通页面处理。保持以 ID 为文件名能够确保重新生成后 URL 永久链接（Permalink）保持稳定。
- **`static/` 资源采用绝对根路径引用**（如 `/covers/x.jpg`）：Astro 通常映射至 `public/`，Jekyll 映射至站点根目录；若部署在包含二级路径的子路径下（如 GitHub Pages 项目主页），需自行配置路径前缀。

## 发布到 GitHub Pages

```sh
npm run deploy -- <canonical> <bundles> <仓库目录> --dry-run   # 预演查看将要发布的条目
npm run deploy -- <canonical> <bundles> <仓库目录>             # 正式部署并写入仓库
```

**`npm run site` 构建的产物不能直接推送到 GitHub Pages 仓库。** 该产物包含完整的 Hugo 工程结构（`content/`、`layouts/`、`hugo.toml`、`static/`、`public/`），而 GitHub Pages 默认以仓库根目录作为静态站点发布 —— 直接推送会导致找不到根目录的 `index.html`。实际需要发布的仅为 `public/` 下编译生成的静态资源。

`deploy` 脚本即负责自动化完成上述发布流程：先在临时目录执行构建（避免构建失败破坏目标仓库），随后将 `public/` 中的产物平铺至目标仓库根目录，并自动处理以下事项：

- 自动写入 `.nojekyll` 文件，防止 GitHub Actions 或 Pages 服务默认使用 Jekyll 过滤下划线开头的静态资源文件。
- 保留 `CNAME`、`LICENSE`、`README.md`、`.git`、`.github` 及 `.gitignore` 等仓库管理文件不受覆盖影响。
- 清理上次部署遗留的陈旧文件，避免残留已失效或被删除条目的孤立页面。

`--dry-run` 模式仅输出预演清单而不执行实际写入。由于发布至公开仓库的操作不可逆，系统在执行正式部署前均会明确打印涉及的内容范围。

### 豆瓣非公开内容的导出控制

默认情况下，系统不会发布以下私密内容；仅在显式传入 `--include-private` 参数时才会导出，并在页面中统一标注 🔒：

| 内容类型 | 默认行为 | 启用 `--include-private` |
|---|---|---|
| 用户在豆瓣主动设置为「仅自己可见」的**日记** | 排除不发 | 导出发布，附带 🔒 标记 |
| **私密豆列** | 排除不发 | 导出发布，附带 🔒 标记 |
| 仅自己可见的**广播** | 排除不发 | 导出发布，附带 🔒 标记 |
| **被豆瓣平台转为私密的日记** | **默认发布** | 导出发布 |
| 可见性状态无法判定的条目 | 排除不发 | 导出发布 |

被豆瓣平台转为私密的日记默认仍会展示发布。其原因在于它此前曾是公开发表的内容；若备份站点顺从平台的屏蔽策略将其隐藏，备份的核心意义便荡然无存。（该处理策略与 NeoDB 导出保持一致。）

`--drop-notes=author,platform,unsure` 参数提供反向过滤能力，用于显式排除特定类型的日记。显式指定的规则优先级高于默认设置，例如 `--include-private --drop-notes=platform` 表示「导出私密内容，但排除被平台锁闭的日记」。

#### 可见性过滤的背景与机制

此前在对日记增加可见性支持时，曾发现过边界遗漏：在豆瓣发布私密日记时，系统会自动同步生成一条广播且正文完全一致。在用户登录态下抓取时，该条仅自己可见的广播也会被收录。若仅对日记页面增加可见性过滤而遗漏了广播侧，私密日记的内容仍可能通过关联广播在首页泄露。

这一经验表明：**权限与可见性过滤规则必须在所有关联数据流中协同执行，防止数据从旁路泄露。**

两处过滤逻辑的设计考量：

- **筛选在 `generate()` 核心模块中执行，而非停留在 `bin/deploy.js` 脚本层。** 若仅在部署发布脚本中做过滤，会导致 `npm run md` 与 `npm run site` 这两条本地生成路径漏掉过滤规则，生成结果无法真实体现过滤效果。
- **当历史 canonical 缺失可见性元数据时，不盲目执行全量剔除。** 解析器 0.13.0 才开始记录广播的可见性；更早生成的 canonical 中广播可见性均为 null。若简单将 null 判定为私密，会导致整条时间线（实测 3429 条）被全部清空 —— 这种过度破坏性的行为不可取。系统基于整个数据集进行综合判断：若所有记录均为 null，则表明该数据生成于旧版解析器，默认全量保留并在终端提示重新解析。

启用私密数据导出时，系统会在 `hugo.toml` 中标记 `includePrivate = true`，主题据此在**所有页面页脚**明确提示「本归档站点包含私密备份数据」。避免因视觉呈现一致而导致用户误判站点的公开性。

示例参考：[sample.doubak.com](https://sample.doubak.com)（[源码仓库](https://github.com/Doubak/doubak-site-generator-sample)）。

生成站点仅为 canonical 数据的消费方式之一，另一途径为 [`doubak-export-adapters`](https://github.com/Doubak/doubak-export-adapters)：基于同一份 canonical 数据生成面向 NeoDB、Letterboxd 与 Goodreads 的标准导入文件。两条链路相互独立、互不干扰。


### 广播的动作句：链接指向与归档范围

`收藏游戏到豆列 游戏购买小账本` 在豆瓣上三个词都能点。解析器把这句话的分段连同
链接一起存进 `action_parts`，生成层按明确规则决定跳转目标：

| 内容分类 | 本地包含对应归档 | 本地未收录对应归档 |
|---|---|---|
| **收录范围**（作品 / 豆列 / 长文） | 站内相对链接 | **不生成超链接**，保留纯文本 |
| **未收录范围**（相册 / 小组 / 榜单 / 影人 / 短链） | —— | 豆瓣原站外链，附带「↗」标记 |

**链接跳转的核心判定规则是「该类别是否属于归档范围」，而非单纯判断「当前本地是否存在」。** 作品条目是本归档旨在替代豆瓣的核心数据，若未收录说明归档数据存在缺失，此时直接提供站外链接会掩盖数据缺口；而作品相册中的图片**明确属于条目公有资产，而非个人数据资产**，归档范围从未宣称收录此类公共照片，因此明确指向豆瓣原站才是合乎预期的严谨做法。

正则匹配严格约束至 URL 结尾：作品 URL 为相册与讨论路径的前缀（如 `…/game/30246116/` 与 `…/game/30246116/photos/`），必须精确区分，防止相册被误判为作品而导致有效链接静默丢失。

### 数据出处标记

每条广播均清晰注明来源出处（对应豆瓣原站页面）。

在 Markdown 中，出处信息以独立的 `[豆瓣原页](… "…")` 段落紧随时间戳标题之后，**避免直接置于标题内** —— 静态站点生成器根据标题文本生成锚点 ID，修改标题会破坏站内固定链接。在最终渲染的 HTML 中，出处标记浮动展示于时间戳行最右端，采用豆瓣图标与站外标记组合展示，兼顾视觉整洁与屏幕阅读器无障碍访问。图标采用内联 `data:` URI，不发起任何外部网络请求。

#### 跨批次稳定的 URL 规范化

在多次抓取之间，部分 URL 会携带动态参数或不同用户别名：

```
追踪参数   …/status/4088086916/?_spm_id=ODIxNjA4NzE    base64 解码后为 uid
用户标识   /people/mewcatcher/  ←→  /people/82160871/  同一账号的不同路径表达
```

规范化处理后，实测 3440 条广播中的 2834 条变动链接实现 100% 稳定对齐。若不进行规范化处理，每次重新生成站点都会产生数千条无实质差异的 URL 变动扰动。由于系统高度依赖 git diff 审查变更，此类无关变动会掩盖真实的修改。

URL 规范化逻辑封装在投影生成层中，canonical 原始数据中依然完整保留抓取当时的原始 URL，保证原始数据的客观真实。

### `--source-repo=<url>`：配置归档站点源码链接

页脚默认包含生成器工具的开源仓库链接。通过传入 `--source-repo` 参数，可在页脚额外增加指向用户自身归档站点仓库的链接：

```sh
npm run deploy -- <canonical> <bundles> <仓库目录> \
  --source-repo=https://github.com/your-username/your-backup-repo
```

该参数显式接收 URL 地址而非布尔开关，避免因写死固定链接而导致用户站点误标他人仓库。传入的地址会写入产物目录中的 `hugo.toml` 配置参数 `[params]`，确保在独立构建时行为一致。

## 列表页面与超链接设计

**各板块均采用标准分页列表呈现。** 例如影视板块包含 2100+ 条记录，单页加载数千张封面会导致严重的性能问题。分页展示中，各条目展示简明状态标签，并在顶部提供全局状态筛选导航 —— 标签上的统计数字基于该板块全量数据汇总计算，而非当前单页条目数，保证统计信息准确且稳定。

**各状态分类为独立的静态页面**（如 `/movie/done/`），而非依赖前端 JS 的临时切换。前端单页筛选只能作用于当前分页的 48 条记录，无法呈现全局状态。采用独立静态页面的方案能够原生支持书签收藏、直接分享、本地 `file://` 协议免 JS 运行以及规范的分页导航。首页上的统计数字亦直接链接至对应的状态汇总页。

**仅针对包含有效条目的状态生成对应页面**：避免生成空无一物的空白页面造成混淆。

**广播组织为平铺展开的时间线**：`/broadcast/` 页面按每页 4 个月（约 90 条广播）分页展开正文，支持连续翻阅，同时各个自然月依然保留独立的永久锚点与固定链接。

### 保证相对链接有效性的两项核心规则

- **同时开启 `uglyURLs = true` 与 `relativeURLs = true`**：若采用默认的目录型链接（如 `book/index.html` 生成链接 `book/`），浏览器在 `file://` 本地协议下打开目录时会直接展示文件系统目录列表，而非加载对应的 HTML 文件。必须显式生成带 `.html` 扩展名的相对文件路径。
- **正文内部跨作品引用指向 `.md` 文件而非硬编码 URL**：链接写为相对路径 `../movie/123.md`，交由静态站点生成器的 link render hook 根据最终的静态输出规则自动转换扩展名，避免硬编码 URL 方案与静态生成配置脱节。

实测全站 4794 个页面中的 94732 个站内链接，无效链接数为 **0**。

## 文本渲染的转义处理

用户短评和广播正文中常包含大量表情字符或特殊符号（如颜文字 `_(:з」∠)_` 或尖括号书名 `<May December>`）。若直接交由 Markdown 引擎渲染，会导致特殊字符被解析为 HTML 标签或排版记号，造成文本丢失或格式错乱。

系统在输出 Markdown 文本时统一执行字面文本转义处理（`plainText()`），确保原始字符完好保留。同时**禁用 `unsafe = true` 原始 HTML 执行**，避免潜在的安全隐患，如实还原纯文本语义。

转义规则通过针对 Hugo 与 CommonMark 规范的 18 组用例进行了严格的双向验证（例如有序列表项转义点号而非数字）。

## 两个输入，一个都不能少

| 数据源 | 职责与内容 |
|---|---|
| canonical | 核心结构化数据：包含标记、作品、长文、广播与豆列 |
| bundle | 静态资源原始字节：canonical 专注于文本，图片二进制数据存储于 bundle 中 |

**除首次自动下载 Hugo 外，数据生成与站点构建不访问网络。** Hugo 已缓存或系统已安装时，即使删除构建目录，也可仅凭原始归档离线完整重建。

## 本地图片归档与关联逻辑

静态站点中的所有图像资源必须完整导出至本地。若直接引用远程 `doubanio.com` 图片，则备份站点依然依赖原平台服务在线，无法满足完全独立可用的归档要求。

封面查找采用**按作品 ID 优先关联机制**：canonical 中的 `cover_url` 通常记录自列表页缩略图，而归档中实际采集的是详情页高分辨率封面（两者在部分媒介上路径规则存在差异）。单纯依赖 URL 字符串比对会导致有效已下载封面被漏配。

对于原平台的「暂无封面」默认占位图，系统判定为无封面，不导出无意义的占位文件。

针对缺失图片的处理，系统明确区分两类情况并分别报告：
- **未采集项（Missing）**：归档中未收录该图，可通过增量补抓补全。
- **损坏项（Unreadable）**：归档中存在记录但底层字节损坏，需重新校验修复归档源文件。

若存在个别图片损坏，系统采用容错降级处理，**不会中断整站生成流程**。建议在构建前通过校验工具先行核对归档完整性：

```sh
node ../doubak-data-parser/bin/verify.js <bundle 目录>
```

## 投影层的只读缓存属性

核心设计原则：**所有衍生数据与变更均以 canonical 原始归档为唯一真相源，投影层纯属只读衍生视图。**

因此，站点生成目录在**每次构建前均会全量清理重置**，杜绝历史陈旧文件的残留，保证生成产物与当前归档数据完全一致。

## 数据保真与边界规则

- **已下架条目作品名保持 `null`**：页面上显示的「未知电影」仅为平台的占位提示而非作品原名，系统不将其伪造为真实标题。
- **未撰写短评时保持正文为空**：不填充「暂无短评」占位符 —— 明确区分「用户未评价」与「数据提取异常」。
- **作品元数据信息原样保留**：导演、编剧与演职员等信息在当前层级不进行武断的字符串拆解猜测，交由专门的 enricher 模块进行可审计的精细化实体识别。
- **首页仅呈现客观统计数量**：不臆测推算「完整性百分比」，完整性证据严格依托 bundle 的 `crawl_state`。
- **文件名采用作品 ID**：条目标题可能存在别名或同名冲突，作品 ID 具备唯一性与稳定性，保证生成页面的 URL 永久链接不受影响。

## 本地站内搜索

站点内置轻量级纯前端搜索页，**无需倒排索引服务、无第三方依赖、不发起网络请求**。

### 原生全量扫描设计

实测归档内可搜索文本约 18.5 万字，采用 JavaScript 原生 `String.includes` 内存全量检索耗时仅 **0.1–0.5 毫秒**，完全实现即输即显。在当前数据规模下，原生字符串检索兼顾性能与简易性，避免了中文分词器与复杂倒排索引的代码维护负担。

### 索引文件格式采用 `.js` 而非 `.json`

浏览器在 `file://` 本地协议下出于安全策略会拦截 `fetch` 与 `XMLHttpRequest` 请求，而 `<script>` 标签不受此限制。若采用 `.json` + `fetch` 方案，站点仅能在 HTTP 服务器环境下运行，在本地双击浏览时将失效 —— 这有违离线独立浏览的设计目标。

因此，搜索索引打包为标准的 JavaScript 脚本（全局赋值形式）。UI 层提供了明确的状态提示：载入中、就绪条目数及加载异常说明。

### 搜索索引的数据解耦

`npm run md` 同样生成 `static/search-index.js`，供任意静态生成器复用。数据中的路径字段 `u` 保持无扩展名格式（如 `movie/1292052`），适配不同的 URL 路由配置。

### 搜索字段与信息权衡

导演、编剧、作者、译者、音乐人、流派等关键元数据均纳入搜索范围。主演字段默认未加入索引，主要基于索引体积与检索相关性的平衡：豆瓣条目演职员列表较为庞大，全量收录会导致索引体积增加数倍；如需开启，可在 `src/search.js` 的 `indexedInfo` 中配置启用。

### 原名与译名同权重检索

作品的**又名**（台译名、港译名与原文名）与主标题享有同等检索权重，例如搜索「重返沉默之丘」与「重返寂静岭」均可准确检索到对应条目。当命中文本位于又名中时，界面会同步显式标出对应的别名文本。

搜索索引仅在独立搜索页面中异步加载，不增加其他常规浏览页面的加载负载。

### 搜索高亮与样式规范

搜索命中关键字高亮显示统一复用 `site.css` 中声明的 CSS 变量，确保明暗两套主题下均具有清晰的对比度与可读性，避免因样式变量未声明导致高亮文本不可见。测试套件包含静态变量引用一致性核验。

## 作品详情与元数据表格

作品页面包含详细的信息表格：导演、编剧、主演、类型、制片国家、语言、ISBN 与出版社等。数据源自**作品详情页**原始抓取，字段键值完整保留平台原始标签。

元数据以正文表格形式呈现而非强行塞入 front matter，避免了复杂特殊字符对 YAML 结构的破坏。该表格与 `douban_meta`（列表页简要字段）互为补充，忠实呈现不同页面层级的原始信息。

## 「历史时间线：言论与状态演变」

在作品页面除展示当前最新短评外，还构建了一条完整的时间线，将**标记的历史修订**与**提及该作品的广播记录**按时间综合串联。

这是本归档的核心价值在页面上的直观呈现：豆瓣标记页仅保留最新一条短评（一旦修改便覆盖历史且平台不留存变更日志），而**广播发布后即固化且带秒级时间戳**，完整记录了标记页上早已被覆盖的历史言论。

实测数据显示出显著的价值补全：

```
仅依赖标记自身修订覆盖的记录         3 条
广播中记录的与当前短评不同的历史言论   342 条（涉及 305 个作品）
最终生成时间线的作品页              2376 / 2940（81%）
```

即使未填写文字短评，状态流转演变（如「想看 → 在看 → 看过」）同样属于条目完整的生命周期记录。

### 历史记录归并机制

同一事件可能在不同数据流中重复体现，系统执行精细化归并：

- **标记行为与同步广播归并**：用户标记作品时豆瓣常同步生成一条广播（带精确秒级时间戳，但常无短评），与标记列表记录（有短评，仅日期精度）相互印证。系统按「状态 + 日期」执行归并，**时间戳取更高精度，短评内容完整保留**。
- **重复广播去重**：用户转播自身历史广播且正文一致时，按正文去重并保留最早时间记录。

归并后若时间戳与短评文字来自不同数据源，系统在页面上明确注明来源（如「时间来自广播，短评来自标记页」），避免产生事实误解。

### 时间线合并的三项核心准则

- **不臆断是否存在「编辑修改」**：实测发现 342 条差异中有 305 条属于正常状态推进（如想看阶段与看完阶段分别发表感想），仅 15 条属于同一状态下的文字重写。若武断标记为「检测到编辑」，绝大多数均属误判。因此系统仅按时间顺序如实罗列，保留原始上下文供读者判断。
- **明确标注数据出处**：严格区分固化快照（广播）与周期性抓取快照（标记列表）。
- **去重优先级**：高精度时间戳优先，同精度下保留最早记录。

若存在跨媒介的作品 ID 冲突，一律不建立推测性关联，确保时间线事实的准确性。

## 广播按月度归档组织

广播记录按自然月进行归档整合：3400+ 条广播中多数为标记流转动作，按月组织能够避免生成数千个零碎单页文件，更好地呈现连续时间线的阅读体验。

月度归档保留了精细的永久锚点链接，月内按时间倒序排列。展示层分页将多个月份展开渲染，兼顾了存储组织的高效与连续翻阅的便利。

广播中的作品链接仅链接至本地已归档条目。若本地未收录（条目未被标记，或存在跨媒介 ID 冲突）则仅保留纯文本，不回退为豆瓣外链。在 ID 存在歧义时一律不建立链接 —— 避免因缺乏媒介类型而误链至错误作品。
